CAN协议

2026-11-16/更新于 2026-11-17
IoV

简述

CAN 是 Controller Area Network（控制器局域网）的缩写，用于汽车内部的实时数据传输。它连接车内的核心部件，如发动机控制单元、变速箱控制单元、ABS 防抱死系统等，都挂在 CAN 总线上实时对话。注意，挂在总线上的绝大多数是电子控制单元（ECU），而不是传感器或执行器本身。

车联网的本质是车内网与车外网（V2X）之间的打通，而 CAN 就是车内网的核心。举三个例子：

  1. 上行：车联网终端（如 T-Box）通过读取 CAN 总线上的报文，获取车速、转速、油量等实时数据，随后通过移动网络发送到云平台或用户的手机 App。
  2. 下行：用户在手机上远程开空调，指令从云端下发到车联网终端，终端再将指令转换为符合规范的 CAN 报文发送到总线上（而非类似 P2P 的点对点寻址，因为 CAN 本质是局域网协议），由特定的控制器执行操作。
  3. 双向：在自动驾驶中，摄像头、雷达等传感器感知到路况后，通过高速 CAN 向转向、制动系统发送控制指令，实现自动化的紧急制动或车道保持。

通信机制

一帧标准 CAN 报文严格按照以下顺序排列：

[SOF 帧起始] -> [ID 优先级] -> [Control 控制场] -> [Data 数据场] -> [CRC 校验场 (15位) + CRC 界定符 (1位隐性)] -> [ACK 应答场] -> [EOF 帧结束]

广播通信

在 CAN 网络中，没有源地址和目标地址的概念。任意一个节点向总线发送数据时，总线上挂载的其他节点都会同时收到这帧数据。

为了避免信息冗余，CAN 报文开头有一个标识符。它代表的不是收件人，而是这条消息与哪些部件相关（比如 0x100 代表发动机转速，0x200 代表车门状态），与之配合的是节点内部的硬件滤波器，其决定了自己需要听哪些 ID 的信息。比如仪表盘和变速箱会接收 ID 为 0x100 的数据，而车窗控制器则会忽略它。

显隐性与仲裁

总线在逻辑上只有两种状态：显性（逻辑 0）和隐性（逻辑 1），前者具有覆盖权，只要总线有一个节点输出 0，整条总线就会被拉到显性状态。后者是默认，只有所有节点均输出隐性位时，总线才呈现隐性状态。其核心作用只有一个：在没有中心调度的共享总线上，让高优先级的通知先行。

在标准报文中，仲裁段由 11 位 ID + 1 位 RTR 组成，在此之前还有 1bit 的起始帧（固定为 0，用于向总线声明有消息将被发送）。两条报文 A、B 并行发送，前者的 ID 位是 001...，后者是 010...，A 比 B 优先级更高，则全过程如下：

  1. 在发送之前总线呈隐性 1
  2. 二者同时发出起始帧 0，总线状态变为 0，并同步时钟
  3. ID 第 1 位均为 0，总线保持 0
  4. B 发了 1，从主线接收的信息却是 0（因为此时 A 发了 0，压过了 B 的 1），于是 B 判断自己仲裁失败，立即停止发送并转换为接收模式，开始听取总线信息（因为 A 的信息说不定对 B 所在的节点也有用处），之后只输出隐性 1，不干扰总线
  5. 此时总线上只剩下报文 A。A 发送 1，总线呈现 1（此时的 1 是纯粹的数据含义（在这里是 ID），不带有仲裁性质），后续总线的状态完全取决于报文 A，直到发送完毕

ACK 应答

广播通信没有指定单一接收者，发送方确定消息是否被他人收到，靠的是帧末尾的 ACK 槽，这依然依赖前文提到的显隐性机制。

在发送完数据和校验码之后，发送者在末尾的 ACK 槽中主动填入一个隐性 1。总线上但凡接收到这帧报文的节点，在 CRC 验证通过后，无论它们是否需要这条数据，都会在同一时刻向总线发送一个显性 0。按照显隐性机制，总线上只要有一个节点正常在线，总线状态就会被覆盖为 0，发送方由此知道消息安全送达。相反，若最终总线状态依旧为 1，发送方会报错并重发。

CRC 校验

汽车内部充满了强电磁干扰，总线上的电平随时可能被干扰反转。CRC 的本质是发送方和接收方事先约定好同一套多项式，对比算出的余数是否一致。

  1. 发送方把所有核心数据拼成二进制数据，用这串数除以协议规定的多项式（15 位 CRC 的多项式为 x15+x14+x10+x8+x7+x4+x3+1 ），算出的 15 位余数就是本次报文的指纹。
  2. 接收方在收到数据的同时对数据做校验，同样算出本地余数。
  3. 若余数一致，接收方则在 ACK 槽输出一个显性 0。若不一致则会向总线发出 6 个连续的显性 0，强行作废整帧数据并逼迫发送方重传。

信号编码

一帧标准 CAN 报文的数据场只有 8 个字节。为了不浪费带宽，每个数据不占用一整个字节，而是按比特紧密排列。要想解析报文数据，就需要 .dbc 文件，由车企提供，来把十六进制报文解析成 JSON 格式的业务数据。

假设车企提供的 DBC 文件对某帧报文的解析定义如下：

格式：SG_ <signal_name> : <start_bit>|<bit_length>@<byte_order><value_type> (factor, offset) [min|max] <physical_unit> <receiver>

（其中 byte_order 为 0 代表大端序，为 1 代表小端序；value_type 为 + 代表有符号，- 代表无符号；<start_bit> 后面的是长度，而非终止比特位）

传统编程中的大小端序只关心字节在内存中的存储顺序，不考虑数据跨字节存储的情况。对于字节串 b"Hello"，b"H" 是第 0 字节。按照大端序，第 0 字节应该被存进高位，所以最终得到的大端整数为 0x48 * 256^4 + 0x65 * 256^3 + 0x6c * 256^2 + 0x6c * 256^1 + 0x6f * 256^0，即 0x48656c6c6f。小端序就是 0x6f6c6c6548。

对于信号编码来说，一个字节中的比特序列为 bit7-0。无论是 Motorola 大端序还是 Intel 小端序，字节内部的比特顺序永远不改变，区别只在于截取哪部分字节以及最终拼接的差异。

对于原始数据 2A 63 94 00 00 00 00 00，解析如下：

  1. 看到 VehicleSpeed 的起始索引是 bit7，长度 13bits。先把完整的 Byte0 拿下来，根据大端序，从高到低截取 5bits：0110 0(000)。去除括号，顺序拼接 得到 0010 1010 0110 0。它已经能被当作二进制数字解析了，因此右对齐，左侧补零，得到 (000)0 0101 0100 1100 -> 05 4C
  2. GearPosition 长度 3bits，截取 3bits 为 03
  3. MotorTemp 是小端序读数，起始索引是 bit16，长度 12bits。先截取 94，后面的 00 从低到高截取 4bits：(0000) 0000，最后 逆序拼接 为 (0000) 0000 1001 0100 -> 00 94

按照 value = factor * raw + offset 的规则，得知 VehicleSpeed 为 135.6km/h ，GearPosition 为 D 档，MotorTemp 为 34.0∘C 。

上述过程可以描述为：从 start_bit 所在的字节（start_bit // 8）开始，向后截取 (字节内偏移 + bit_length + 7) // 8 个字节（大端偏移为 7 - start_bit % 8，小端偏移为 start_bit % 8）。 大端序解释时，跳过顶部偏移后向下截取 bit_length 比特；小端序解释时，跳过底部偏移后向上截取 bit_length 比特。

通信行为

在 Linux 中模拟 CAN 总线是很方便的，其内部提供了一个名为 vcan 的虚拟网络接口驱动，使得我们可以在本地完成 CAN 报文的收发。

此外，Python 的 can 模块支持操作总线，为底层硬件接口提供了便捷的 API。
